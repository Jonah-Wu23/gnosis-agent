关键假设有三个：继续冻结受测模型权重；AutomationBench 的原始任务与评分器保持固定；不同任务之间存在可复用的接口操作经验。撤掉前两个假设，研究对象就变了；撤掉第三个假设，自进化的收益只能留在当前任务，持续学习这条主线便不成立。

**GNOSIS 改为允许模型连续修复、组合经验的自主进化系统，以可执行组件承载经验，以真实激活边界限定影响范围，并把省下的验证费用重新投入修复。** 剩余预算集中投入这条路线。

方案依据全部调研材料、先导报告、README、科研计划及实际代码，采用 prism-vector-synthesis 方法，从模型学习、执行系统和实验识别三个角度推演。

**复用已有修复机制，围绕持续进化中的验证成本形成研究贡献。**

GPT 调研提出的“先实际修复，再提炼经验”和 Alphaxiv 对费用浪费的判断最有价值。Claude 材料强调的自主探索，对改造搜索空间有帮助。Leapspace 的参考文献可补充相关工作，但其中若干治理式约束会把系统引向大量人工规则。Gemini 材料中的抽象推演，没有提供比现有执行证据更直接的改进依据；涉及隐藏模型状态的设想也不适合当前 API 条件。

采用以下机制：

- **采用连续执行反馈，取消每个微小改动立即完成整题的要求。** 部分进展可以保留在工作版本里，继续修复剩余问题。
- **允许模型生成可执行能力。** 包括批量读取、翻页、数据计算，以及多步工作流程；经验也可以保留为文字，形式由模型选择。
- **以实际执行依赖确定作用域与影响面。** 记录组件首次生效的位置，据此确定历史任务需要重新执行的部分。

复用 **StarHarness 的进化循环和适配器契约**。仓库已有提议、选择集评估和留出评估的实现，可直接承担自主修复流程的基础。[StarHarness 开源仓库](https://github.com/ServiceNow/StarHarness)

ACE 用官方实现承担经验记忆基线；SAGE 用于预先安排的固定候选配对比较。开发选择集支持反复修复，最终留出集独立评估冻结版本，统计结论对应具体的版本比较。[ACE](https://github.com/ace-agent/ace)、[SAGE](https://arxiv.org/abs/2609.36043)

模型自由尝试，系统记录改动的传播范围，实验用独立任务检验学习收益。

解决办法可以借鉴三个领域的结构：数据库事务把工作版本与正式版本分开；反馈控制让执行结果持续修正下一次动作；增量构建按依赖关系决定重算范围。对应到 GNOSIS，就是**工作版本自由迭代、执行反馈持续返回、发布版本按影响范围验证**。三个机制共同服务于一个进化循环。

具体实现应一次性完成以下改造。

1. **建立真正的自主修复工作区。**

   给进化模型访问当前可编辑实现、任务轨迹和学习集评分反馈的能力。允许它查看成功任务，执行来源题，修改已有组件，也可以组合多个改动。

   每次执行后的真实失败结果直接返回同一修复过程。修复翻页之后仍漏发通知，就继续修复通知；中间的有效改动保留在工作版本里。来源题未完成时，不消耗独立验证预算。

   搜索单位可以是一个组件，也可以是一组相互配合的组件。模型自主决定修改范围，完整保留经验的操作过程与执行证据，另用短摘要支持检索。

   模型在预算内决定继续修复、改变假设或转向另一道任务。模型读取轨迹后自主调度任务，兼顾跨领域覆盖与修复价值。

2. **把组件接入真正能够改变执行的位置。**

   统一暴露工具发现、调用前处理、调用结果处理这些扩展位置。成功响应和错误响应都进入组件可见的执行反馈。

   模型可以创建可调用的操作函数，例如完整读取表格、按实际字段计算结果、完成写入后读取确认。执行组件通过原有能力接口操作环境，权限和评分规则保持固定。

   文字知识仍然有价值，尤其适合解释业务范围。涉及稳定计算或重复操作时，可执行组件能直接承担工作。由进化模型根据执行结果决定采用什么形式。

   模型自主选择局部或 `GLOBAL` 作用域。通用改进执行全局验证，局部经验按实际影响范围验证。

3. **同时修正推理预算和终止状态。**

   当前 8192 输出上限已经多次被推理耗尽。新版本将**单次输出上限提高至 32768**，给模型完成推理与动作生成的空间，按实际美元消耗管理任务预算。

   分别记录截断、正常完成和工具执行失败；空响应且 `finish_reason=length` 的执行记为截断。

   这些运行条件统一用于所有实验组，并重新获得基线。旧的 50% 保留为先导结果，新实验中的提升从修正后的基线计算。

4. **在成熟版本上做选择，让部分进展留在工作区。**

   工作版本可以包含尚未完成整题的改动；达到来源题完整成功后，再进入独立选择集。

   发布单位采用当前整组组件的版本。开发选择集的执行反馈可用于继续修复；最终留出集在版本冻结后独立评估。

   SAGE 用于预先安排的成熟版本比较。工作区内连续编辑、执行和积累有效改动，成熟版本统一接受配对评估。

   配对复测采用预定的对称规则，胜负结果使用相同的执行次数与统计方法。

**论文最有价值的创新，应集中到“激活边界如何使验证可复用”。**

已有工作提供工具修改与经验提炼机制。GNOSIS 的核心贡献是建立组件激活位置与历史执行依赖的联系，解决以下问题：

> 持续进化时，能否根据一个改动第一次实际影响执行的位置，精确确定哪些历史执行必须重跑，并将节省的预算转化为更多有效学习？

这里有三个必须成立的条件：

- 组件激活前，模型看到的提示、工具目录和观测内容保持一致。
- 组件通过已登记的扩展位置开始执行，并从该位置起读写共享状态。
- 历史记录包含实际经过的扩展位置，新增组件也能据此判断首次可能生效的位置。

运行时通过扩展位置确定**组件何时开始对执行产生可见影响**，据此计算实际作用域。

未进入新组件激活位置的历史执行复用既有证据；进入该位置的执行从那里起重新验证。路径发生改变后，后续执行全部纳入影响范围。新增组件的激活条件同样用于检查旧轨迹，识别首次可能生效的位置。

满足环境状态与执行前缀可恢复条件时，还可以复用激活之前的执行前缀。无法恢复的任务从头执行。这能把方法从简单的服务级筛选推进到可解释的执行依赖机制。

这里的理论结论应写得精确：

\[ C_{\text{验证}} \approx \sum_{i\in \text{受影响任务}} C_{\text{需要重新执行的部分},i} \]

**撤掉“激活前不可见”这个假设，作用域外不受影响的结论立即失效。** 例如新组件虽然尚未被调用，但已经出现在全局工具目录中，它就可能改变模型的第一步选择。

验证费用由受影响任务及其重执行部分决定。未受改动影响的历史证据直接复用，使预算集中用于检验新增能力。[原科研计划](<E:/AI/GNOSIS Agent/docs/GNOSIS-科研计划.md>)

这条路线给予模型充分自由：可以改动较大的工作流程，也可以产生全局经验。作用域越广，验证费用越高；有效局部经验因此获得更多迭代机会。**有限预算在这里成为学习资源分配机制的一部分。**
