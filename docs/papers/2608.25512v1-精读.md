## 标题
A Programming Paradigm for Spatiotemporal Composability（面向时空可组合性的编程范式）

作者：Yifan Shi¹ᐧ²、Wei Zhang¹、Tianyi Cui²（¹北京大学，²DeepSeek-AI）

## 研究问题
- 解决的问题：动态组合（运行时加载、卸载、重配置组件）缺乏形式化基础。静态组合有丰富的理论框架，动态组合的工程实践只有粗粒度替代方案：操作系统以进程为粒度提供时间维度的恢复（重启），容器编排以服务为粒度提供空间维度的依赖管理。重启丢弃进程内积累状态（缓存、连接、中间计算），重建耗时秒到分钟级，还要冗余副本维持可用性。
- 论文把问题分解为两个正交维度：
  - 时间可组合性（temporal composability）：组件被移除时，它对共享环境做过的修改能被完全、安全地回滚。
  - 空间可组合性（spatial composability）：组件能声明、发现、解析彼此依赖，依赖拓扑变化时生命周期得到协调。
- 重要性（论文给的两个动机场景）：
  1. 插件系统：以 VSCode 为例，扩展宿主无法单独卸载单个扩展的代码，top 100 扩展中 87 个含可执行代码、移除必须重启宿主；只有 7 个声明 `extensionDependencies`，扩展间交互返回无类型的 `any`，没有结构化契约（数据取自 2026 年 6 月的 Marketplace 统计）。
  2. 自进化 agent harness：未来的 harness 会在持续服务中生成并替换自己的组件。没有时间可组合性，每次自我修改都要整体重启，频繁重启积累大量不可用时间，进行中的任务反复被打断，错误的修改还可能摧毁恢复所需的进程本身；没有空间可组合性，各模块只能用临时手段感知依赖的出现、消失与身份变化，朴素的代码替换会静默破坏依赖方或引入重载时才暴露的循环依赖。

## 核心方法
- 整体思路：effect 系统形式化"计算如何修改环境"，coeffect 系统形式化"计算如何依赖环境"，恰好对应两个维度。但经典 effect/coeffect 系统是静态工具：effect 在词法固定的作用域内追踪、编译期由 handler 消解；coeffect 标注在执行前确定的上下文上检查。论文的做法是把这两套概念结构实体化（reify）为运行时可操作的机制：
  1. revertible effects：每个上下文变换携带一个逆变换，逆由运行时持有，组件移除时恢复上下文。
  2. reactive coeffects：组件以 specification 声明所需 coeffect，每次上下文变化按该 specification 分类为 activating / deactivating / neutral，驱动组件激活与停用。
  3. context paradigm：effect context 与 coeffect context 统一为单一 context type，一切 effect 与 coeffect 经由它中介；中介诱导出观测等价（observational equivalence），在该等价下不同组件的 effect 交错执行互不干扰。
  4. 把两者组合成 component 概念，给出动态组合演算（九条规则的操作语义），元理论把单组件的时空可组合性提升到任意交错的全系统。
- 与已有方法的核心差异：
  - 对比 monadic effect 库（ZIO、Effect-TS）：那些系统要求程序写进 effect 类型里才能获得追踪，且服务被撤回后其操作留下的痕迹原地保留；本范式作为普通宿主代码上的 overlay 追踪 effect，并给每个 effect 配逆、随 provider 来去重新解析依赖。
  - 对比开发者手写清理（OSGi 卸载回调、Command 模式的 undo、saga 补偿、React useEffect）：那些方案的逆操作是与操作解耦的、无强制力的义务，遗忘即静默泄漏；本范式中逆随 effect 应用一并返回，恢复是系统不变式。
  - 对比 DSU / Erlang / Webpack·Vite HMR 的状态前向迁移：Cordis 走"回滚旧组件 + 干净重放新组件"路线，不需要手写迁移函数，支持彻底卸载，代价是组件自有内存状态不随重载存活（论文承认这一点，把 DSU 式迁移列为未来工作）。

## 模型 / 算法要点
- Revertible effects（第 3.1 节）：
  - effect context `E ≜ C × (C→C)`：当前状态 + 反向累加器（迄今所有 effect 之逆的复合，即恢复函数）。
  - twisted composition：正向按序复合、逆按反序累积，构成 monoid；`track` 是该 monoid 到上下文变换 monoid 的同态（Thm 5），`recover` 满足 soundness invariant（Thm 7），追踪不改变前向行为（Thm 4）。
  - effect function `F ≜ C → C × (C→C)`：在应用点返回 per-state 的逆，witness 只要求逆在"它被应用的那个状态"回滚该 effect（Def 8），比全程可逆要求弱得多；effect composition 把 monoid 结构提升到 `F`（Thm 10/11）。
  - effect iterator：每次迭代产出（新上下文，逆，continuation），是具体化的 delimited continuation，直接映射到主流语言的 generator/yield；卸载时按 LIFO 应用累加器，每步逆恰好面对自己应用产生的状态（Thm 16）。
- Reactive coeffects（第 3.2 节）：
  - coeffect context `K`：依值部分函数（每个键绑定类型化值），`get`/`set` 带前置条件（不能重复提供、不能撤回不存在的依赖）。关键协同点：`set` 的类型就是 effect function，因此依赖注册自动继承追踪与回滚。
  - specification `σ` + `notify`：把每次变迁分类为 activating/deactivating/neutral；满足谓词可判定（定义域有限），且所有变更都经过 effect function，满足性变化在每个 effect 边界可检测——这是反应性的代数基础。
  - isolation：realm 表把逻辑键映射到存储 realm，同一键在不同上下文解析到不同值（论文称之为运行时 ad-hoc 多态），`isolate` 派生子上下文，不动共享表，无需逆。
  - interception：每个键配一个 metadata monoid，访问时合并组件声明的 metadata 与上下文携带的 metadata（右偏，外层可覆盖组件声明），provider 按合并结果调整行为；用于访问控制等横切关注。
- Context paradigm（第 3.3、3.4 节）：
  - 统一上下文 `X ≜ X × (X→X) × K`，自相似递归，支持层级组合（父上下文聚合子级 effect，形成树形控制结构，任意嵌套装卸）。
  - context-mediated iterator 只允许三种 stage：operation（对某键绑定值的操作）、provision（安装绑定，产出 restriction 作为逆）、instantiation（实例化新组件）。所有交互必须经过 context，这是纪律的全部形式内容。
  - 观测等价 `≈`：一个键的等价由它的操作集生成的"测试"定义——任何测试序列在两个值上行为一致则不可区分；它是受所有操作尊重的最粗等价（Lemma 32）。恢复不再要求物理状态复原（堆布局、生成名本来就复原不了），只要求恢复到观测等价。
  - effect independence：两个迭代器的全部变换（正向映射与产生的逆）两两交换（Def 42）；成对独立时，以任意排列顺序应用各自的逆都回到初态（Thm 43）。
  - Thm 47 把独立性归约为：两者的 provision 键集互不相交 + 共享键可交换。键的交换性证明作为 coeffect 的第三个成分（witness，Def 46）由提供方承担；不同键的操作天然独立（Thm 45）。中间件链这类有序结构不交换，路由表、事件监听器这类"各自注册各自条目"的键可交换；接口发布的 outcome 越少，等价越粗，键越容易交换——论文指出这与 scalable commutativity rule 同源。
- 动态组合演算（第 4 章）：
  - component = `(σ, π, F)` 三元组：声明读什么（specification）、写什么（provision）、做什么（witnessed effect function）。
  - fiber 是 component 的实例化，携带四态生命周期（对应实现的 INACTIVE / LOADING / ACTIVE / UNLOADING，失败扩展增加 FAILED）；registry 是父指针成树的 fiber 表。
  - 九条规则：编排侧 O-Insert / O-Retire / O-Remove（外部输入，O-Insert 强制 single-source 纪律：一个键至多一个可能 provider）；生命周期侧 L-Begin / L-Iter / L-Finish / L-Divert / L-Leave / L-Unload（系统自发）。
  - target view 与 committed view 的比较驱动一切变迁：依赖被替换和依赖消失走同一条退出路径；L-Unload 的 guard `¬relied(μ)` 把 provider 的撤回推迟到所有解析到它的消费者停用完毕，消费者在整个 teardown 期间仍能读到该依赖。
  - 实例化原语（Def 52）：组件可在自身 effect 中实例化子组件，其逆是子 fiber 的 O-Retire，因此卸载父组件级联到子组件。
- 元理论主要定理：
  - Thm 64（preservation）：每条规则保持 registry 良构。
  - Thm 68（recovery exactness）：fiber 的 episode 内任意时刻应用其累加器，效果等于该 fiber 的步骤从未发生（up to ≈），其他 fiber 任意交错不影响。
  - Cor 69（terminal recovery）：episode 关闭后 fiber 的表为空，O-Remove 不丢弃任何绑定。
  - Thm 70（ordering）：fiber 只在依赖齐备时开始 transition；provider 的 episode 严格包含消费者的 episode；消费者 episode 内绑定只被声明该键的 fiber 的操作移动。
  - Thm 71（resolution coherence）：一次 transition 不跨越两个解析——target 改变时 fiber 经 L-Divert 退出 transition。
  - Thm 73（progress）：在 precedence 无环、迭代器长度有界、fiber 名有限的假设下，无死锁且生命周期步数有界，任意极大生命周期步序列终止于静默态。
  - Thm 80（confluence）：任意动态历史静默后的状态，等于同一最终配置从头静态装配的状态（up to 重命名与 ≈）。论文称这为"动态历史不留痕迹"，是声明式 loader 增量 reconciliation 合法性的来源。
- 实现（第 5 章，Cordis）：
  - `ctx.effect`（Algorithm 1）：execute 引擎驱动回调为 effect iterator，逐步折叠逆；armed 守卫保证 dispose 至多触发一次；子 effect 的 dispose prepend 到父上下文的累加器。所有上下文变更（`ctx.set`、`ctx.use` 等）都归约为这一个原语。
  - 三个 symbol 槽：`@@store`（realm→值）、`@@isolate`（键→realm）、`@@intercept`（键→metadata）；`notify` 沿 fiber 表找出声明了变更键且 realm 相同的 fiber 触发 refresh。
  - 生命周期（Algorithm 5）：refresh 重算 target 摘要（以 provider 的 uid 而非值标识解析，uid 不复用），reload/unload 惯性互链（transition 一旦开始必须完成，迭代边界上可做部分回滚）；unload 先置 UNLOADING 停止提供服务（L-Leave 的实现），再等待被通知的 dependents 到达 INACTIVE（guard 的运行时形态），最后运行累加器。
  - Proxy 属性访问（Algorithm 6）：沿 fiber 链向上授权，已声明未提交抛 INACTIVE_ACCESS，未声明抛 UNDECLARED_ACCESS，读取的是 fiber 自己的 view——这是 Thm 70 成立所依赖的设计。
  - 声明式 loader：entry 记录 id / url / isolate / intercept / config / disabled 六个字段，恰好覆盖 support set 读取的全部内容；按变更字段做最小扰动 reconciliation（config 交给组件自行 diff，group 按子 id 做 keyed diff 并递归）。
  - HMR（Algorithm 8-10）：固定点算法分类 accepted/declined 模块（陷入 import 环的默认 declined），检测依赖树触及变更模块的 stale entry，事务化重载——任何模块导入失败即恢复缓存并从备份重建，不需要 Webpack/Vite 式开发者标注的 accept 边界。

## 实验设置
- 任务：PL/SE 方向的理论 + 系统论文，无 ML 意义的任务、数据集、指标、baseline。
- 验证由两部分构成：
  1. 第 4 章元理论：九条规则上的保全、恢复精确性、顺序性、解析一致性、进展、汇流定理，全部附证明。
  2. 第 5.3 节 Koishi 案例研究：四年开发、4000+ 社区插件的生产生态，论证 (a) 表达力——整套系统建在 context 原语上，框架只提供聊天领域词汇；(b) 通用性——同一模型同时承载服务端机器人与浏览器端控制台两个独立 Cordis 应用；(c) 时间可组合性——控制台里禁用插件即原地回滚其 effect，HMR 保存即重载且不影响系统其余部分；(d) 空间可组合性——切换存储后端、重连适配器只重新激活解析发生变化的依赖方，依赖缺失的插件静默等待。
- 消融或额外分析：无消融。第 6 章讨论代替定量评估：系统边界（acquisition 可回滚、emission 越界，只能 withhold 或 compensate）、服务多路复用（broker 吸收 provider 切换的扰动，支撑负载均衡、滚动更新、跨进程调用）、访问控制与沙箱、宿主语言需求分析（闭包、模块注册表或动态链接、DI、Proxy/描述符/宏）、循环依赖处理、依赖版本化、与语言及 OS 的协同设计。

## 主要结果
- 论文声称的主要收益：
  1. 单组件的时间/空间可组合性经元理论提升为全系统任意交错下成立的全局保证；
  2. 汇流定理保证动态装配等价于最终配置的静态装配，orchestrator 增删改换组件不必担心历史路径；
  3. Cordis 实现与形式模型逐条对应（Table 2 给出理论符号到运行时构造的完整映射）；
  4. Koishi 证明该范式能承载完整生产系统，并让插件作者"不写卸载路径也获得有序清理"。
- 结果是否充分支持 claim：理论部分证明链完整（我按结论级核对，未逐步验证证明）。案例部分作者自己划定了边界：单一生态、单一宿主语言、观察性证据，属于"存在性与采纳度"结果，抽象开销与开发者生产率的量化对比留作未来工作。理论与实现之间有一条明说的缝隙：逆确实回滚（Def 8 的 witness）、键确实可交换（Def 46 的 witness）都是组件作者的义务，运行时不验证。

## 优势
- 方法层面：
  - 问题分解干净且对偶：时间 ↔ effects、空间 ↔ coeffects，两个维度各取所需后由统一 context 合流，`set` 天然是 effect function 这一观察让两套机制互相成就。
  - per-state 逆 + 观测等价把"恢复"从物理不可能转化为接口设计问题：少发布 outcome 即可加粗等价、让键变得可交换，给了组件作者一条可操作的设计程序（Def 31）。
  - 从单累加器到全局定理的晋升路径清晰：independence 覆盖不相交组件，entanglement（消费关系）由 guard 与 LIFO 顺序兜住，分治完备。
- 实验层面：元理论覆盖保全、精确恢复、顺序、一致性、无死锁、终止、汇流，链条完整；实现给出全部关键算法伪代码；案例是真实四年生产生态，且作者对证据强度保持诚实。
- 研究价值层面：首次为 agent harness 自我修改给出形式化根基；插件卸载、HMR、依赖注入、热更新被收进同一个范式；第 6.7 节（语言与 OS 协同设计）指出了后续系统研究的明确路线。

## 局限
- 证据不足处：无性能基准、无对照架构的受控比较；witness 缝隙（错误的手写逆、不可交换的键会静默破坏全局保证）没有运行时或工具链闭合手段。
- 适用范围限制：
  - single-source 纪律：一个键同一时刻至多一个 provider，多 provider 要靠 realm 或 broker 模式绕行；
  - 依赖循环在模型内不解决，直接表现为相关组件永久不激活（可静态预测、可加载时报告，第 6.5 节建议拆细组件消环，代价是组件数量可能平方级增长）；
  - 组件自有内存状态不随重载存活，想跨重载保留的状态必须放进更长寿命的 coeffect；
  - 依赖链接只有名义链接（按键名），接口漂移与键碰撞问题只有 peer dependencies 这类半工程方案，结构兼容判定留为开放问题。
- 可能的失败场景：emission（已发出的字节、已扣的款）在系统边界外，逆触及不到，只能 withhold 或 compensate；补偿基于更粗的等价，交换性需要重新证明。汇流定理对失败 fiber 不成立——某个迭代是否抛错取决于它遇到的状态，不同调度可能得到不同的静默态（差异仅在该 fiber 的生命周期状态）。

## 复现难点
- 数据或环境：复现理论部分不需要数据。复现实现需要 Cordis v4（Koishi 生产用 v3，loader 经过重新设计）；论文正文未附仓库地址，需自行确认 `@cordisjs` 系列包与 v4 代码的公开状态。
- 训练细节：不适用（无训练过程）。
- 评测细节：无公开评测脚本，案例研究无可复现的定量协议。
- 工程复杂度：核心机制在 Algorithm 1-6 中完整给出，数百行量级可实现语义原型；真正的难点有二——(1) 每个原子 effect 的逆必须自己写对，范式不提供帮助；(2) 在非 TypeScript 宿主上需要重造 Proxy/模块注册等中介机制（第 6.4 节给了各语言的对应件清单）。形式化部分（Def 1-81、Thm 至 80、大量 coinductive 论证）完整复现证明需要扎实的 PL 功底。

## 对当前研究的启发
面向 GNOSIS Agent 这类自进化 harness 场景：

- 可直接借鉴：
  1. 把 harness 的工具套件、权限沙箱、会话状态、记忆系统、子代理编排各自建模为 `(σ, π, F)` 组件，模型自生成的修改就收敛为 O-Insert/O-Retire 级别的受控操作，进程不用重启，进行中的任务不被打断。
  2. `ctx.effect` 模式作为 harness 唯一副作用原语：注册工具、挂事件、改配置、起子任务全部返回 dispose，父组件卸载自动级联到它实例化的子组件。错误修改可以整体撤回，恢复进程本身不受波及——正中第 1.2.2 节点名的失败场景。
  3. 声明式 entry（id/url/isolate/intercept/config/disabled）作为 harness 持久层：配置树即系统权威记录，格式简单到 agent 可直接读写，reconciliation 的正确性由 Thm 73/80、Cor 69 现成供给。
  4. guard 的卸载顺序：替换被依赖的模块时，先让消费方走完 teardown 再撤回绑定，且消费方 teardown 期间仍能读到旧依赖。热替换工具模块、记忆模块时这是最需要的顺序保证，实现只有三行关键代码（Algorithm 5 的 Line 10/14/25）。
  5. 能力式访问控制：inject 声明静态可知，orchestrator 加载时审批；interception metadata 可在不改组件代码的前提下收紧权限（如把某社区组件的文件访问压成只读），且不触发任何 reload。
- 可对比验证：
  - 若 GNOSIS 已有自己的热重载/插件机制，可用 Thm 68（恢复精确性）、Thm 70（卸载顺序）、Thm 73（死锁与终止）、Thm 80（历史无关性）逐条作检查清单，找出保证缝隙。
  - 实验设计上可做故障注入对照：有 guard 与无 guard 的卸载顺序下，观察消费者 teardown 读到失效依赖的失败率——这是论文没有做、但 harness 场景很自然的定量验证。
- 可作为反例或边界案例：
  - 依赖循环 → 永久不激活：harness 需要静态检测并在加载时报告给 agent，否则自我修改可能制造出静默瘫痪的组件簇。
  - 组件内存状态不跨重载存活：agent 的 session 状态必须放进更长寿命的 coeffect（独立的状态组件），否则每次自我修改都丢失上下文。
  - emission 不可回滚：agent 已发出的外部动作（写过的文件、发出去的消息）只能补偿，harness 设计时要把"动作发出"与"记录安装"显式分阶段。

## 是否值得精读
- 标签：值得精读
- 判断理由：命中阅读准则多项——研究问题与自进化 agent harness 直接相关（论文把它列为两大动机场景之一和头号未来验证方向）；方法上提供了新的形式化框架（revertible effects + reactive coeffects + context paradigm）与新建模思路；元理论链条完整且有生产级实现双重支撑；对正在做 agent harness 的工程有直接可借用的机制（`ctx.effect`、guard、声明式 reconciliation、能力式访问控制）。阅读建议：第 3-4 章证明密度极高，目标若是使用 Cordis 或移植范式，读第 1、3（结论级）、5、6 章即可覆盖全部工程内容；第 4、7 章留给需要发展理论或写 related work 时再读。
