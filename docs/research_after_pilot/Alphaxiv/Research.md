**这次先导最明确的失败是：3 个最终候选没有一个修复自己的来源题，导致知识库始终为空；因此，GNOSIS 想证明的作用域节省、持续增益和遗忘控制，实际上还没有进入可检验状态。** 问题首先在“从失败中提出有效改动”，而不是阶段末统计门禁太严格。

下面先按你的报告诊断，再结合原论文讨论前人方案。我重点检索并阅读了反馈归因、知识编译、可执行约束、候选筛选和统计门禁相关工作。

## 1. 不好在哪里

### 1.1 核心学习环节没有产出，而不是基准选错了

| 环节       | 本次证据                             | 可以得出的判断                           |
| ---------- | ------------------------------------ | ---------------------------------------- |
| 基准余量   | B1 严格通过 15/30，均分 0.6406       | 有提升空间，没有重现此前基准饱和的问题   |
| 候选修复   | 来源题翻转 0/3；候选得分为 0、0、5/6 | 当前提议机制没有产出经来源题验证的修复   |
| 独立迁移   | 24 对原始结果合计 2 胜、2 负、20 平  | 存在个别变化，但没有一致的改善方向       |
| 知识累积   | 接受单元 0 个                        | 没有发生持续积累，不能检验遗忘           |
| 作用域     | 3 个最终候选全部 GLOBAL              | 核心的局部影响面机制没有得到有效测试     |
| 阶段末检验 | 配对数 0，`not_applicable`           | 没有输入，不是“统计检验否定了方法”       |
| 费用       | 本次先导 $1.14194，累计 $4.66219     | 执行完成，但在阶段预算内没有获得有效单元 |

**这是一份可信的机制失败记录，但还不是“作用域化自进化无效”的实验。** 账本、隔离、恢复和评分核验完成，是工程上的成功；不能替代学习效果。

另外，3 个候选全部来自 Finance。它们不能代表全部 15 道失败题，也不足以判断跨领域知识是否可学。

### 1.2 三轮失败不是同一种失败

这是报告中最有价值、也最需要保留的区分：

- **第 1 轮：要求行动，但没有发生所需写入。** 知识说要结束探索、完成登记与通知，来源题却没有写入。问题可能是指导太泛、触发时机不对，或者模型根本没有落实。
- **第 2 轮：组件被调用，但几乎没有产生新的干预。** 231 次组件调用，只有 1 次新增提示事件；该事件后模型仍继续探索，没有通知。这里有“触发稀疏”和“提示不被落实”两个不同瓶颈。
- **第 3 轮：知识被落实，但知识解释使任务失败。** 模型确实包含了 Delta，并独立应用两个标记；然而原装断言要求排除 Delta。**这是知识正确性问题，不是采纳问题。**

所以，统一采用“加强提示”“改成代码”或“多跑几轮”，都不能同时解决三种失败。尤其第 3 轮，把错误业务解释编译成代码，可能只是更稳定地做错。

### 1.3 采纳率目前不足以支持整体判断

29 次知识激活中，只有 2 次被判定为一致或不一致，其余 27 次未判定；组件行为也只有 1 次可判定事件。

这支持“发现了两个未落实案例和一个落实但错误的案例”，**不支持“总体采纳率很低”这一量化结论**。报告保留未判定是正确的，下一步要改的是观测口径，而不是补造比例。

“注入后下一步”经常是端点搜索，本来就不该立即完成登记、通知或报告。合理的观察对象应当是：**从触发开始，到相关动作发生或任务结束的行为窗口**。

### 1.4 验证预算花在了尚未证明有用的候选上

3 个候选都没有通过来源题，却仍做了 24 次独立题执行和 2 次确认复测。

这些运行对机制诊断有价值，但对晋升没有价值：按照当前规则，来源题不翻转已经足以拒绝候选。**这使昂贵回归检查没有被便宜的修复检查筛掉。**

提议与自修复费用约占本次先导的 26.7%，候选执行约占 73.3%。眼下应优化的是“有效修复／美元”，而不是继续增加回归覆盖。

## 2. 可能的原因有哪些

我会按证据强弱，优先考虑以下六类原因。

### 2.1 失败反馈不足以定位真正原因——最优先排查

提议器看到轨迹、环境报错和 scalar partial_credit，却看不到断言文本。这符合你的部署设定，但也造成一个关键缺口：

> 它知道“没有成功”，不一定知道“哪条业务解释错了”。

第 3 轮最典型。5/6 的反馈无法直接告诉提议器：应该修正项目范围，而不是加强低毛利标记或邮件完整性。

这里不能简单归结为“模型推理能力不足”。更直接的假说是：**反馈没有足够信息区分多个可行但互斥的修复方向。**

计划中“A2 在同基准已有增益，所以自进化涨分失败概率很低”的判断也偏乐观。已有研究证明某个模型、某种 harness 和反馈配置可以改进，不等于你当前的提议器与编辑空间一定能改进。

### 2.2 提议器把局部问题概括成了过宽的 GLOBAL 规则

3/3 最终候选都选择 GLOBAL，说明当前流程没有把作用域作为真正约束。

诸如“及时结束探索”“包含所有符合范围的项目”，很容易从单题失败中归纳出来，却缺少：

- 明确的应用或端点；
- 触发前提；
- 适用业务条件；
- 反例和禁用条件；
- 可观察的预期动作。

这会同时降低修复精度、增加无关任务干预，并直接消解验证费用优势。

**GLOBAL 不是一个普通作用域，而是放弃局部边界的特殊选择。** 应要求它具有跨任务的重复证据，不能仅凭一条失败轨迹就采用。

### 2.3 文字说明缺少执行约束，但当前组件也没有真正替代文字

第 2 轮的 T 组件虽然是可执行组件，实际产生的有效干预仍然是 nudge；它没有替模型完成参数检查、阻断重复探索或核验完成条件。

要区分：

1. **代码生成提醒**；
2. **代码验证动作**；
3. **代码执行确定性子步骤**。

只有后两者才显著减少对模型“愿意遵循说明”的依赖。组件调用次数多，不等于行动被有效约束。

### 2.4 注入时机和失败时机不匹配

当前局部知识在“首次成功调用作用域接口”后注入。这能支持干净的边界，但有两个盲区：

- 如果失败发生在接口发现或参数错误阶段，成功调用尚未发生，知识就可能来不及介入。
- 如果真正风险出现在后面的写入、结束或重复探索阶段，第一次成功调用时的提醒可能过早。

这是待验证的机制假说，不是本次已经证明的根因。可以通过原始轨迹定位：**知识出现时，关键错误已经发生了吗？**

### 2.5 小样本和单侧确认使效果难以辨认

24 对中 20 对持平，有效比较信息很少；两个初次退化在复测中恢复，也说明结果存在随机波动。

此外，“只重跑输掉的候选一次，恢复就不算确认退化”是一个操作性规则，**不是对称的效应估计**。若胜出不确认、对照不复测，这种选择性复测会让确认后的结果偏乐观。

它没有造成此次零接受——来源题已经挡住了全部候选——但在未来出现接受单元时，会影响阶段末检验的可信度。

### 2.6 研究设计中还有两项尚未暴露的结构性问题

**第一，固定 8 对不天然适合局部微小改进。** 在零负、惩罚系数为 1 的情况下，单侧精确检验至少需要 5 胜，才能达到 $p<0.05$。一个确实只修好一两类任务的局部单元，可能永远无法在 8 对中获得足够胜出。

你计划写的“1 负需要 7 胜”在显著性层面成立，但当前退化率上限为 0 时，有负就仍然不能接受。

**第二，历史没有触达某端点，不等于未来不会触达。** 静态白名单排除作用域，可以支持严格无影响；有限历史轨迹的“未触达”只能支持概率估计。首个请求字节一致也不足以证明整个作用域外运行不受影响，尤其 GLOBAL 单元从一开始就改变上下文。

因此要区分：

- **静态保证不受影响**；
- **经验判断低概率受影响**；
- **抽样检查中未发现退化**。

这三者不能合并成“保证不遗忘”。

### 3.2 前人对“反馈不够好”的证据，比对“记忆不够多”的证据更直接

[Evo-Harness](https://www.alphaxiv.org/abs/2608.15071) 的反馈消融很贴切：在同一 CL-Bench 设置下，自生成成功判断使结果低于不进化；环境最小反馈只有小幅改善，丰富的外部诊断反馈改善更明显。[Feedback Ablation](https://www.alphaxiv.org/abs/2608.15071v2?page=8)

<!-- Bar Chart: Evo-Harness：CL-Bench 反馈消融 -->

但同一论文在另一软件修复基准上，最小反馈略优于丰富反馈。因此结论不是“反馈越详细越好”，而是：**反馈必须足以定位可迁移的错误，同时避免让知识绑定到单题答案。**[Feedback Granularity](https://www.alphaxiv.org/abs/2608.15071v2?page=8)

对 GNOSIS，我建议保留“不提供隐藏断言”的主设定，但把学习输入组织成：

- 任务明确要求的约束；
- 真实错误与响应；
- 哪些必需动作没有出现；
- 哪个可观察状态没有达成；
- 修复假说与反例。

如果必须用断言或正确答案才能找到根因，应另设**特权反馈诊断臂**。它能回答“反馈不足是不是瓶颈”，但不能混入主方法来声称无标注自进化成功。

### 3.3 与你同基准的成功工作，确实有可借鉴方案，但不能照搬增益预期

[StarHarness](https://www.alphaxiv.org/abs/2608.24804) 在 AutomationBench Finance 上报告了明显改善，但论文明确说明：使用 Finance-100、不同 agent harness，以及领域目标完成比例指标，不能直接与原装基准设置比较。其 57.1%→83.2% **不是你报告中的严格通过率提升**。[Evaluation Setup](https://www.alphaxiv.org/abs/2608.24804v1?page=5)[Finance Results](https://www.alphaxiv.org/abs/2608.24804v1?page=9)

它与你的关键差异包括：

1. 从多条失败中按失败类型分层；
2. 提议器能修改较宽的工程表面；
3. 有来源题翻转的早停筛选；
4. 有提议器不可见的选择任务；
5. 采用结构化表格操作、日期与财务计算工具来压缩探索。[Search Protocol](https://www.alphaxiv.org/abs/2608.24804v1?page=3)[Learned Repairs](https://www.alphaxiv.org/abs/2608.24804v1?page=7)[Search Compression](https://www.alphaxiv.org/abs/2608.24804v1?page=8)

**最值得立即移植的是它的廉价筛选顺序和确定性子步骤，不是它的大范围代码搜索。**

### 3.4 “代码化”有前人支持，但必须分清约束和业务判断

[AutoHarness](https://www.alphaxiv.org/abs/2603.03329) 证明，外部程序可以把动作合法性从模型自由判断中分离出来；[Agentic Harness Engineering](https://www.alphaxiv.org/abs/2604.25850) 则提供了执行时约束比早期文字提醒更可靠的具体案例。[Code Constraints](https://www.alphaxiv.org/abs/2603.03329v1?page=3)[Runtime Guard](https://www.alphaxiv.org/abs/2604.25850v4?page=28)

适合你优先代码化的是：

- 按 schema 验证参数；
- 根据明确协议处理分页；
- 检测重复且无进展的探索；
- 记录写入后是否得到成功响应；
- 对任务授权的写入执行回读检查；
- 固定日期或算术计算。

不适合未经验证就代码化的是：

- “所有项目都应纳入”；
- “现在必须发邮件”；
- “某个字段为空就删除它”；
- “重复调用就自动重试写入”。

这些可能改变业务语义或产生重复副作用。**执行代码仍必须调用原装接口、保留真实错误，不能改评分器，也不能利用隐藏状态。**

## 4. 我建议下一步怎么做

**先暂停原计划的六臂正式实验，做一轮“修复能力诊断”，不要仅给旧流程追加预算。** 原始先导保持原样，新版本明确登记改动。

### 第一步：零新增模型请求，重新整理现有失败证据

把 15 道 B1 失败按“最早未恢复错误”分类，而不是只按领域分类：

- 接口发现／调用错误；
- 探索无进展；
- 缺少必需写入；
- 写入后没有核验；
- 业务范围／规则解释错误；
- 暂时无法定位。

同时把单元效果拆成四层：

> **知识出现 → 触发条件成立 → 目标行为发生 → 官方任务通过。**

第 3 轮已经表明，第三层成立不保证第四层成立。

对于 Delta，逐字比对任务指令、可见数据与评分要求：若指令支持排除，是候选解释错；若指令确实要求包含，才是契约错配问题。无论哪种，都保留官方分数，另记诊断，不能事后改成绩。

### 第二步：只测试“能否修复来源题”，先不做 8 题回归

从不同失败类型挑代表题；每次只变一个变量：

- 具体、带触发条件的局部文字知识；
- 对同一知识采用更贴近关键动作的注入时机；
- 对可确定的规则采用可执行检查。

先验证来源题；失败立即停止该候选。出现翻转后，再做预先规定的重复确认与同失败类型迁移检查。不能不断重跑直到成功。

这一步的目标不是证明泛化，而是先区分：

> **错误知识、正确但未触发、触发但未落实、落实但未修复。**

### 第三步：出现有效局部单元后，才重启影响面门禁

此时再处理：

- GLOBAL 的证据要求；
- 静态可排除任务与经验低风险任务的区分；
- 对称、预登记的确认规则；
- 最终知识库下的阶段末重跑；
- 微小局部效果所需的检验样本量。

固定最多 8 对可以作为廉价筛查，但不能同时承担“证明微小增益”和“保证总体零退化”两项任务。

### 第四步：同步保留预算对齐的简单重试基线

把同等额外费用花在冻结 Agent 的独立重跑或顺序修订上，反馈权限与 GNOSIS 相同。

若知识修复没有比这种简单办法更稳定、更便宜，就不应继续扩大自进化实验。[Rethinking the Evaluation of Harness Evolution](https://www.alphaxiv.org/abs/2607.12227) 的结果正说明，复杂进化可能只是较昂贵地实现了多次尝试。[Scaling Comparison](https://www.alphaxiv.org/abs/2607.12227v4?page=6)

还有两处计划应更新：本版本 AppWorld 执行数是 0，不是预算表中的“40 题已执行完”；阶段末“不显著就弃权”与“不显著仍保留单元”也要统一，明确区分临时知识库与正式知识库。

**最终判断：GNOSIS 当前最该修的是“反馈归因—局部候选—来源题早停”这条链，而不是放松门禁。** 我会优先借鉴 [StarHarness](https://www.alphaxiv.org/abs/2608.24804) 的来源题筛选、[Evo-Harness](https://www.alphaxiv.org/abs/2608.15071) 的带证据和触发条件的知识编译，以及 [Agentic Harness Engineering](https://www.alphaxiv.org/abs/2604.25850) 的可验证执行干预。只有新版本能重复修复来源题并迁移到同类独立题，才值得恢复正式实验。
